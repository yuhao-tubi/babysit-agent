# Domain glossary — PR Babysitting Agent

Ubiquitous language for this project. Glossary only — no implementation detail.

- **Poll cycle** — one pass of the daemon: discover the PRs you authored (skipping `ignoreRepos`), fetch all their feedback grouped by thread, and upsert a Thread-unit for every thread with actionable, non-resolved feedback. Idempotent: unit existence is derived from live GitHub state each poll, not from first-sight.

- **Session** — a PR and all its Threads. The PR-level grouping for triage and the dashboard; it is *not* itself a status-bearing unit (its status is rolled up from its Threads). Discovered PRs in `ignoreRepos` (e.g. `owner/some-repo`) are skipped entirely.

- **Expired Session** — a Session whose PR has merged or closed (fallen out of the live open set the poll cycle observes). It is *retained*, not deleted: its Threads and history stay queryable and it is surfaced in the dashboard's own **Expired** section. The pipeline never acts on an expired Session's Threads. Re-appearing in the open set un-expires it.

- **Thread** — the unit of triage and the decision unit. One per `(PR, threadKey)`: an inline review-comment thread (root + replies), a review summary body, or a standalone issue-tab comment. A Thread carries one Verdict, one Pre-push gate run, and the thread-attempt loop guard, and moves through a status lifecycle. A Thread GitHub-marked **resolved** is never acted on — skipped at both creation and just-before-action.

- **Feedback item** — a single comment belonging to a Thread: an inline review comment, a review summary body, or an issue-tab comment.

- **Author class** — `bot` or `human`, determined deterministically from the GitHub user type and a configurable login list, fixed to the Thread's **root** comment author. Drives the reply policy.

- **Verdict** — the agent's categorical decision for a Thread: `propose`, `reply`, `escalate`, `amend_pr_body`, or `dismiss`. There is no numeric confidence; routing is the verdict plus the objective gate result. `propose` (a code change), `amend_pr_body` (a description change), and `reply` (a comment to post) all yield a **Proposal**; `escalate` means a decision is needed and carries no diff (it may list **options**); `dismiss` (see below) yields nothing at all. No GitHub write — push *or* reply — happens without an explicit **Approve** (except `autoPushClasses`).

- **Dismissal** — the Verdict for a Thread that asks for **nothing**: a bot's review-summary header with no findings, boilerplate or metadata-only text, pure approval or praise ("LGTM"), or an echo of the agent's own earlier reply. It is the one Verdict that yields **no Proposal**: the Thread goes straight to `resolved` with no reply drafted, no diff, and **no GitHub write of any kind** — not even resolving the inline review thread, which stays the owner's call via **Mark resolved**. `dryRun` is therefore moot for it. It exists because such Threads used to park a "nothing to address" reply Proposal that cost the owner a click to clear. It is emphatically **not** a way to disagree: any concrete claim about the code — even a nit, even a suspected false positive — is still a `reply` (with cited proof), `propose`, or `escalate`, because the narrow-by-design bar is *"was anything asked?"*, never *"is the reviewer right?"*. Applies to every author class, except **CI** (a failing check always has an ask, so a CI Verdict can never be a dismissal). Reachable two ways: from the grounded Verdict, or from the **Pre-triage** fast path.
_Avoid_: ignore (means the Instruction that drops a Thread), reject, decline, resolve (the status, and the owner's manual action). Note two neighbouring uses of the same word that are **not** this: a **dismissed reply** is the owner waving away a Proposal's reply part, and a **dismissed** Verified risk is one the confirmer disproved. Unqualified, *Dismissal* means the Verdict.

- **Pre-triage** — a text-only pre-filter that runs before the Verdict's read-only checkout and can only ever return a **Dismissal** or "carry on". It is shown the Thread's comment text and nothing else — no code, no PR description — because *"does this text ask for anything?"* is answerable from the text alone, and withholding the rest keeps it from judging code it hasn't read. Not an agent run: one direct model call, no tools, no worktree, so a no-ask Thread is settled in seconds instead of holding the repo's serial queue for minutes, and it is bounded by a hard timeout so a stalled call falls through rather than replacing the wait it was meant to remove. **Fail-open by construction**: every uncertainty, malformed answer, or API failure falls through to the full grounded Verdict — it can decline to decide, but it can never be the reason real feedback is dropped. Skipped for CI Threads.
_Avoid_: prefilter/screening (use Pre-triage), classification.

- **Proposal** — a frozen, owner-reviewable artifact parked on an Awaiting-approval Thread. It can carry up to two **independently-approvable parts**: a **change** (a gate-passed code diff built against a recorded `baseSha`, or a rewritten PR description) and a **reply** (a drafted comment to post). The owner approves them separately — pushing the code does not post the reply, and vice versa; either part can be approved, and the reply can be copied-out to refine by hand or dismissed. A `reply`-kind Proposal carries only the reply part. It is the durable truth for the Awaiting-approval state — restart recovery re-renders it and never re-runs the verdict. **Approve** acts on exactly these bytes. Approving **either** part (the change is applied, **or** the reply is posted) resolves the Thread — the owner has acted, so it no longer blocks on the other part; the un-acted part stays approvable (the frozen Proposal is kept until both parts are settled — applied/posted or dismissed/absent). A further kind, **Manual plan**, is not approvable.

- **Manual plan** — the fallback when a `propose` change is too large to apply autonomously, triggered two ways: the fix agent hits its max-turns cap, **or** its diff touches more than `maxProposalFiles` files (default 5, counting source + test + config alike — the size guard that keeps every auto-applied change an easy, reviewable fix; the fix agent is also softly prompted to bail early on large refactors). Instead of erroring the Thread, a read-only planning pass runs in the same worktree and emits a self-contained implementation brief; it is parked as a `manual_plan` Proposal and the Thread is marked **blocked**. The daemon **never pushes** a manual plan — the owner copies the brief from the dashboard and runs it in Claude Code on the PR branch by hand. Like any Proposal it survives restarts; **Approve** is a no-op for it.

- **Approve** — the owner's one-click acceptance of a Proposal part, and the **sole write path**. Approving the **change**: for a code Proposal, re-check the frozen diff still applies to the current HEAD, re-run the gate, then fast-forward push the exact reviewed bytes; for a description Proposal, `gh pr edit --body`. Approving the **reply** posts the drafted comment. The two are approved independently and neither implies the other. Nothing else pushes or comments on a PR (except the verbatim **Reply on GitHub** escape hatch, and classes opted into `autoPushClasses`, which auto-push and self-ack).

  The apply-check has three outcomes, and only one of them is a dead end. The frozen bytes are tried exactly first (WYSIWYG); on mere **context drift** a 3-way merge **re-seats** the same edit, and the re-seated diff is what is gated, logged, and pushed — provided it touches no file the frozen diff didn't (a merge that widens the blast radius is not the change that was approved). When upstream edited the **same lines**, the reviewed edit is genuinely gone: the daemon then **auto-re-proposes** rather than parking on `blocked` for the owner to hand-type "redo it" — the fix agent is re-run against the new HEAD, is shown the diff that no longer applies so it re-applies the same *intent*, and is explicitly licensed to make **no change** if upstream already addressed the feedback (an empty rebuild lands `blocked`, never an auto-resolve — "already fixed upstream" and "the agent found nothing" are indistinguishable from here). The rebuild is a Proposal like any other: **nothing is pushed**, because the new bytes are not the bytes the owner read, so it parks for a second Approve. Only this same-line conflict auto-rebuilds; a malformed or unmergeable frozen diff is a fault in our own artifact, not the branch moving, and stays `blocked`. A re-propose replaces the parked Proposal, so a reply part the owner already **posted or dismissed** carries over onto the new one — otherwise a comment already on GitHub would be offered for posting a second time.

- **Options** — for an `escalate` Verdict, the concrete choices the agent sees. In the dashboard they are clickable chips that pre-fill the Instruction box; selecting one does not run the agent by itself.

- **Pre-push gate** — the objective self-verification a change must pass: the repo's build/test, or a repo-type validator when there is no test suite. Run when a Proposal is built, and again at Approve time against the current HEAD. CI-failure fixes run the **full** gate (`pre-build` → typecheck → lint → the failing check's class). Owner-reviewed proposals run a **light** gate scoped to the diff: for a monorepo it first rebuilds **only the workspace packages the diff touched** (`lerna run build --scope`, not the whole `pre-build` fan-out) so the app typechecks against fresh sibling `.d.ts` — otherwise a diff that adds an export to a workspace package (e.g. `@myorg/some-pkg`) makes `typecheck-app` report the PR's own new symbols as "missing" — then runs an incremental `typecheck-app` and lints only the changed files.

- **Escalation** — a Thread that needs your judgment (a decision, not a change). It is marked **blocked**, fires a notification (coalesced per PR), and waits for your Instruction.

- **Instruction** — your freeform input on a blocked / awaiting-approval Thread from the dashboard. A freeform Instruction always **re-proposes** (builds a fresh Proposal to review — it never pushes); `reply:` parks that text as a **reply Proposal** you review and post (it does not post directly — that is the verbatim **Reply on GitHub** button's job); `ignore` drops it. The box has an **AI refine** helper — a one-shot direct Claude rewrite of the box text (apply a note like "make it firmer"), not an agent run; the refined text returns to the box for you to edit and submit.

- **Revision** — the **Revise** button on a parked Proposal's card: the agent is re-run and shown its OWN current output (the diff, the reply draft, the proposed description) plus your note, so it improves what you just read instead of re-deciding from the feedback. It is the third rung above **AI refine** (one-shot text rewrite, no agent) and a freeform **Instruction** (full re-propose, prompt does not include the current diff). Each Proposal part is revised independently, and a Revision is never a write path: a revised change re-runs the gate and re-parks for **Approve**; a revised reply still waits for **Post**. The change part of a `code`/Manual-plan Proposal is revised as an Instruction re-propose (so it inherits the fix→gate loop); a reply draft and a `pr_body` description are text, so they are revised by a read-only agent run that patches only that one field of the frozen Proposal.

- **Thread attempt** — the count of autonomous (auto-pushed) fixes already pushed for a Thread. Bounds the fix↔re-review loop for `autoPushClasses`: after the configured maximum, the next round escalates instead of fixing. Owner-approved pushes are the owner's call and aren't loop-limited.

- **Auto-push classes** — `autoPushClasses` config: author classes (`ci`/`bot`/`human`) allowed to push without owner approval when the gate passes. Default `[]` — everything parks for Approve. `risk:"high"` always vetoes auto-push regardless.

- **Branch advanced** — an annotation on a **waiting** Thread (`blocked` / `awaiting_approval` / `error`) listing the commits pushed to the PR branch after the Thread stalled. A branch push never re-opens a frozen Thread (that invariant stands), but the owner may have landed the fix by hand; the poller snapshots the head when a Thread first enters a waiting state and, once the head moves past it, records the new commits (shown under Feedback in the dashboard). It never changes status — the owner still resolves/acts. Cleared automatically the moment the Thread is re-worked or resolved.

- **Auto-generated brief** — a **reviewer**-role PR's overview (+ diagrams + Verified risks) started by the poll cycle instead of by the owner's Generate click, so it is already waiting when the PR is opened. Config `overview.autoGenerate` (default on), at most `overview.autoMaxPerCycle` (default 2) per cycle, **newest PR first** — a ceiling that keeps a day-one backlog from launching a stampede of agents. Deliberately narrow: **author** PRs are excluded (they run on the expensive default model, and the owner wrote the code); a **stale** brief is not a trigger (the panel shows the stale hint and the owner clicks Regenerate); and a **`failed`** brief is never auto-retried, so one broken PR can't consume a slot every cycle. It is the same code path as a click (`requestOverview` → per-repo `overviewQueue`, same in-flight guard, status, and SSE events), so it performs NO GitHub writes and can't preempt owner Thread work. Because a `failed` brief is terminal for automation, restart recovery distinguishes the two interrupted cases: a `generating` row with **no prose yet** resets to `idle` (truthfully never generated → picked up next cycle), while one that already had prose resets to `failed` (keeping its readable text). Started only from the daemon's poll **loop**, never from `pollOnce` — the `poll-once` CLI stays a free read-only check that spends no tokens.

- **Verified risk analysis** — a reviewer-role-only artifact produced by the **same** Generate run as the PR overview (whether the owner clicked it or the poll cycle auto-started it), in the shared read-only worktree, right after the overview (fed it as context). Two sequential read-only agent passes: a **finder** surfaces the handful of grounded risks a reviewer must scrutinize (each with a severity `level`, a cited `file:line` permalink, an illustrative diff hunk, and an optional mermaid chart) into `overview/risks.json`; an adversarial **confirmer** re-investigates each and writes verdict-only records (`confirmed`, optional `level` override, cited `rationale`) into `overview/risks-confirmed.json`. The server merges them by `id`: a match becomes **confirmed** or **dismissed**; a finder risk with no matching record is shown **unverified** (never silently dropped); an orphan confirmer id is ignored. Its status (`ready`/`failed`) is **independent** of the overview's — a failed risk stage never blanks a ready overview, and a confirmer failure degrades to all-unverified/`ready`. It performs NO GitHub writes (`dryRun` does not gate it). The reviewer framing surfaces **Verified risks**; the same engine on author PRs surfaces **Blind spots** (see below), which **replace** the overview's former inline author `## Risks` prose — that inline section is dropped for authors, so a PR has a single risk surface per role.

- **Blind spot** — the author-role counterpart to a **Verified risk**: a grounded, cited behavior *your own change* causes whose consequence is test-invisible harm (a downstream query breaks, a metric stops reflecting truth, an experiment pollutes unenrolled users). The primary job is **harm-hunting** — a Blind spot is worth surfacing whether or not the PR description mentioned it. It must clear a **two-part materiality bar**: the harm must be both *invisible at PR time* (not caught by CI or by reading the diff — excludes nits and CI-catchable bugs) **and** *manifest away from the change* (a dashboard, experiment readout, downstream consumer, or other code path — the "drift-to-a-distance" signature). A plain in-diff bug is out of scope (other bots cover those); Blind spots are narrowly about drift that escapes to a distance. It decomposes into two grounded facts (the code does X; X has consequence Y) plus an open **question** about intent, and carries a short **why-it-matters chain** so the author can judge the stakes; the agent verifies the facts (cited `file:line`) but never adjudicates intent. The PR body is *one input, not the gate*: it enables an advisory **not-in-description** tag (a lens, not the reason the finding exists), so an empty or stale body degrades gracefully to pure harm-hunting rather than producing noise. Distinguished from a Verified risk by role and framing (risk = severity, for a reviewer scrutinizing someone else's code; Blind spot = downstream harm on your own change). Produced by the **same** finder→confirmer engine on author PRs, sharing its storage and panel; the engine, not the concept, is what is reused.
_Avoid_: risk (reserve for the reviewer framing), gap, oversight.

- **Adjacent suggestion** — a *generative* counterpart to a **Blind spot** (which is defensive): not "the code does X, which will hurt" but "while you're already touching this, you could *also* do Y." It points at an *absent good*, not a present harm — e.g. you're editing an analytics event, so logging one more field alongside would be cheap and useful. Deliberately kept a **separate class** from Blind spots: a harm must never be confused with a nice-to-have. It does **not** clear the Blind-spot two-part test (nothing is wrong, so there is no at-a-distance harm) and has no disprovable fact for the confirmer to verify, so it uses its **own bar**: an Adjacent suggestion qualifies only if it is *genuinely adjacent* (enabled by **this** diff — the touched code is right there — not general "your code could be better") **and** *cheap relative to its payoff* (one more field in an event you already emit, not a rearchitecture). **Deferred** — named now, built after the defensive Blind-spot path earns trust.
_Avoid_: nit, improvement, refactor.

- **Explanation** — a **Thread**-grained, read-only, on-demand artifact: the agent's grounded markdown answer to the question raised in one Thread, with mermaid charts in fenced blocks where the shape of the thing is what makes it hard. Its audience is **you**, the PR author — it is decision support for replying (or for understanding your own code), *not* a draft reply, and it has **no write path at all**: it is never posted, so it needs no gate, no Proposal, and no Approve. Deliberately **not** a `VerdictAction` (every action ends in a GitHub mutation; this one mutates nothing) — it is modeled on the other read-only owner-facing artifacts, with its own status column, own head-sha, in-flight guard, and `overviewQueue` run. Triggered by **Explain** on any Thread in any status, including a Thread you rooted yourself (a note-to-self is the purest case). The agent's output format is a markdown **file** (`explanation.md`) rather than JSON, because the payload is one long prose document and there is no per-item structure to justify a schema; grounding is enforced mechanically — a doc citing no line-anchored permalink into the current checkout is discarded as `failed`, since an ungrounded explanation reads as authoritative and is worse than none. An optional follow-up **question** re-asks and *replaces* the previous answer (one-shot artifact, no transcript). Staleness is **soft**: after a push the prose still holds and only the permalinks rot, so the doc keeps showing with an "older head" hint rather than being withheld (unlike a **Blind spot**, which is blanked when stale).
_Avoid_: chat, conversation, answer draft, reply.

- **Takeover** — a **Thread** rendered as a copy-paste prompt for another coding agent, for when you have decided to do this Thread by hand. It is a **pure projection of state the daemon already holds** — the original feedback conversation, the **Verdict** and its rationale, the parked **Proposal**'s diff, the **Explanation** — assembled into one markdown document, so it is deterministic, instant, and available on **every** Thread in **any** status: nothing is generated, nothing is stored, no agent runs, and it is coupled to no lifecycle. Distinguished from a **Manual plan** by having no agent behind it (a Manual plan is *planned* by a read-only agent pass and parked in the Proposal slot as a fallback; a Takeover is *formatted* from existing rows) and from an **Explanation** by audience (an Explanation is prose for you; a Takeover is input for a doer). Its imperative is deliberately **thin and neutral**: it states what each included artifact *is* and where it came from, and never editorialises about what should be done with it — you copied it out precisely because the judgment is now yours. Read-only by construction: no gate, no Approve, never pushed or posted.
_Avoid_: handoff (means a conversation-compaction skill in this repo), manual plan (the agent-planned Proposal fallback), dossier, brief.

- **Stack** — a chain of Sessions in one repo that build on each other: a PR sits **on top of** another when its **base** branch is that PR's **head** branch. Detected from branch topology alone, so it holds for any stacking tool (`gh stack`, Graphite, hand-cut branches) and needs no tool metadata; two PRs that merely share a base (both onto `master`) are *not* a Stack. Derived at read time from the live PR rows and never persisted, like the Session's rolled-up status. It groups the dashboard sidebar, annotates a Thread with where its PR sits, and is **an input to the Verdict**: feedback on one layer is feedback on a slice of a larger change, so the verdict agent is given the whole chain (see *Whole-stack verdict* below). It is still deliberately *not* an input to the gate or the push path — a fix only ever lands on the Thread's own PR branch, and holding a mid-Stack push until its parent merges is a separate decision, not this one. Members are labelled by **depth** (`L1`, `L2`, …) rather than position, because a Stack can **fork** — two PRs cut off the same parent share a level, and "2 of 4" would invent an order that doesn't exist. Detection is built from *every* live PR, not just the ones the sidebar renders, so a mid-Stack PR with no Threads still links the chain; a merged bottom PR is Expired and simply drops out, leaving the PRs above it as a shorter chain.
_Avoid_: train, series, dependent PRs, epic.

- **Whole-stack verdict** — how a Thread on a **Stack** layer is triaged: the verdict agent is told the whole chain (each member's depth, number, title and head branch, and whether it sits **below**, **above**, or **aside** — the other arm of a fork), and every other layer's branch is fetched into the checkout's clone so it can diff them. A layer-blind verdict is wrong in both directions: the line a reviewer points at may have been introduced *below* (already merged into this checkout, so it reads as this PR's), and a "this is unused / has no caller / has no test" claim is often answered *above* (not in the checkout at all, so it reads as true). So the agent is given both scopes — this PR's own change (`git diff origin/<parent head>...HEAD`) and the stack's (`git diff origin/<root base>...HEAD`) — and one hard limit: a fix can only be pushed to *this* PR's branch, so when the correct change belongs to another layer it **escalates** naming that PR instead of proposing a cross-layer edit. Standalone PRs get none of this (no briefing, no extra fetch).
_Avoid_: stack fix, cross-stack push, restacking.

- **Review state** — what GitHub itself says about a Session's approvals, refreshed every Poll cycle and shown on its dashboard row: the review **decision** (`APPROVED` / `CHANGES_REQUESTED` / `REVIEW_REQUIRED`) plus the number of **people** whose latest review is an approval. There is deliberately **no "N of M approvals"**: the required-approval count lives in branch protection, which the user's `gh` token cannot read (both the protection and rules endpoints 404), so the row states what GitHub told us and stops rather than inventing a target. Distinct from the babysitter's own **Awaiting-approval** status, which is about an owner **Approve** of a Proposal and has nothing to do with GitHub reviewers.

- **Check state** — the failing/pending check summary for a Session's head, refreshed every Poll cycle from the same single `gh pr view` call as the head, base and Review state (so it costs no extra request). Counts **every** check, not just the CI allowlist, because the question it answers is "is my PR red" — it is a display summary and is deliberately independent of the **CI Thread** path, which stays on its own read and only ever creates Threads for allowlisted, actionable failures. Quiet by construction: a badge appears only when something is failing or in flight, never when all checks pass. As-of-last-poll, and suppressed on an Expired Session, whose last-seen check state froze just before it merged.

## Status lifecycle

`pending` → `in_progress` → (`resolved` | `blocked` | `awaiting_approval` | `error`)

A **blocked** Thread (a decision is needed) waits for an Instruction. An **awaiting_approval** Thread holds a frozen Proposal and waits for Approve (or a revising Instruction); both survive daemon restarts. New activity on a `resolved` or `error` Thread re-opens it to `pending` for a **fresh** Verdict (subject to the thread-attempt loop guard) — but the **agent's own** comments never count as new activity. The agent posts under your login (`@me`), so the login alone cannot separate its acks from a note you typed: every comment the agent posts carries an invisible **agent marker** (an HTML comment), and only marked items are discounted. A comment *you* wrote is real input — a note-to-self on your own PR is work for the agent, so a Thread you rooted is triaged like any other, and a group consisting entirely of marked items is never made into a Thread at all (a top-level ack posts as a new comment id, so nothing else would catch it). New activity on a `blocked`/`awaiting_approval`/`pending`/`in_progress` Thread just attaches the new items — it doesn't reset state. A Thread GitHub-marked resolved is moved to `resolved` (dropping any Proposal) and skipped.

Restart recovery is keyed on the most durable artifact, never on replaying a stored Verdict decision: an interrupted Approve re-applies the frozen Proposal; an interrupted Instruction re-proposes; a Thread with a frozen Proposal re-applies it; otherwise the Verdict pipeline re-runs from `pending`. An `awaiting_approval` Thread is left untouched — its Proposal is the durable truth.
